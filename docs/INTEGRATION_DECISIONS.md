# Решения Backend 2 для интеграции AI Engine

Реализованы схема Supabase, Auth API, каталог/заявки/модерация и клиент AI Engine. 21 ноября 2026 года связка локального Backend 2 с AI Engine на `https://ai-engine-demo.onrender.com` и настоящими Supabase Auth/Storage/PostgreSQL прошла 37 проверок. Тестовый аккаунт, файлы и записи платформы удалены; технические записи запусков и вымышленного tenant остаются в движке, где нет API их удаления. LLM работает в mock-режиме; интерфейс подключён локально, облачный хостинг Backend 2 ещё предстоит. Ниже зафиксирован контракт этой стороны для согласования с владельцем AI Engine.

## Тенант и роли

Для MVP один владелец представляет один бизнес: `company_id = profiles.id = auth.users.id` владельца с ролью `business`. Таблицы заявок, запусков и файлов ссылаются на этот профиль; ограничения требуют совпадения владельца и пользователя. Клиент не выбирает произвольный tenant в запросе запуска — сервер выводит его из проверенной сессии.

| Роль платформы | Возможности | Роль движка |
| --- | --- | --- |
| `business` | Свой профиль, заявки на подключение, свои файлы и история | `admin` своего tenant |
| `developer` | Свой профиль, заявки на публикацию, собственные черновики карточек | Доступ к исполнению пока не выдаётся |
| `admin` | Просмотр профилей, каталога и заявок для модерации | Не выдаётся автоматически |

Администратор платформы не получает автоматического доступа к резюме и истории бизнесов. Модерация выполняется через Backend 2 и транзакционные RPC с собственной проверкой живой сессии и роли из БД; прямой `UPDATE` от клиента запрещён. Сервисный ключ не нужен. Только доверенный оператор базы может назначать платформенную роль `admin`. Auth API отклоняет регистрацию с `admin`; триггер базы дополнительно ограничивает первоначальную роль значениями `business`/`developer`.

Командные аккаунты потребуют таблиц `companies` и `company_members` и миграции существующих tenant ID. Текущие проверки `company_id = user_id` тогда надо заменить проверкой членства; одну эту проверку убрать недостаточно.

## Таблицы и права

| Таблица | Назначение | Доступ клиента |
| --- | --- | --- |
| `profiles` | Роль и данные владельца | Свой профиль; изменение только `display_name`, `company_name` |
| `agents` | Каталог и соответствие `engine_slug` | Всем опубликованные и будущие карточки; разработчику также свои черновики |
| `connect_requests` | Подключение бизнеса к карточке | Создать свою `pending` заявку к опубликованному агенту; читать свои |
| `agent_submissions` | Заявки разработчиков | Разработчик создаёт свою `pending` заявку и читает свои |
| `agent_runs` | Метаданные вызовов | Только читать свои; пишет сервер |
| `agent_files` | Соответствие Storage и `engine_file_id` | Только читать свои; пишет сервер |

Одна заявка подключения на пару `(company_id, agent_id)`. В этом API заявка рассматривается один раз; повторное решение возвращает 409. Повторная подача той же пары также возвращает 409; повторное открытие/отзыв подключения потребует отдельного процесса. `approved`/`rejected` требуют `reviewed_by` и `reviewed_at`, которые база заполняет от текущего администратора. При одобрении публикации создаётся карточка `coming_soon` со ссылкой в заявке, всё в одной транзакции. При конфликте slug изменения откатываются, заявка остаётся `pending`.

`agents.engine_slug` уникален и соответствует slug движка (`marketing`, `support`, `hr`). Статус `published` пока разрешён только с непустым `engine_slug`: внешним агентам нужен отдельный адаптер исполнения. До его реализации такие карточки остаются черновиками или `coming_soon`. Наличие `engine_slug` не заменяет проверку доступности агента в движке.

Перед запуском Backend 2 проверяет роль бизнеса, статус карточки `published`, `engine_slug` и заявку `approved` именно этой компании. Авторизация исполнения не обеспечивается одной возможностью прочитать публичную карточку.

## Токен и транспорт

| Claim или настройка | Значение |
| --- | --- |
| `sub` | ID проверенного пользователя Supabase |
| `company_id` | ID его бизнес-профиля |
| `company_name` | `profiles.company_name` |
| `role` | `admin` для владельца бизнеса |
| Алгоритм | `HS256` |
| `aud` | `ai-engine` |
| `iss` | `marketplace-backend` |
| `iat`, `exp` | Сейчас и сейчас + 300 секунд |
| Таймаут HTTP | 180 секунд |

Секрет — отдельные случайные минимум 32 байта, хранится в окружении только двух серверов. Нужен адрес `ENGINE_URL` и защищённое согласование секрета с владельцем движка. Обе стороны задают одинаковые `aud` и `iss`. Браузер вызывает Backend 2. Автоматический повтор запуска не включать: у движка нет ключа идемпотентности, а таймаут не доказывает, что выполнение не произошло. Состояние после таймаута требует сверки.

## Журнал запусков

В `public.agent_runs` нет полей для запросов, ответов, резюме, фрагментов базы знаний или произвольного JSON ошибки. Сохраняются UUID запуска и карточки, tenant и пользователь, slug/версия, статус, язык, режим/модель, токены, оценка стоимости в USD, время, HTTP-статус, машинный код ошибки, request ID и счётчики файлов/источников.

`engine_run_id = response.run_id` или `error.details.run_id`. Backend 2 создаёт строку `running` до исполнения, затем обновляет ту же строку по её ID и владельцу; отдельной вставки после ответа нет. Уникальный `engine_run_id` защищает от привязки одного ответа к разным строкам, но не от повторного исполнения HTTP-запроса. Для сетевого сбоя допускается `engine_run_id = NULL` и статус `engine_unreachable`; для ошибок до создания запуска — `rejected`/`error` с NULL. Статусы успешного выполнения требуют ID движка. Отсутствующие значения токенов/стоимости остаются NULL; ноль означает известное нулевое потребление. `total_tokens` рассчитывается базой. При сбое финального обновления API возвращает `audit_saved=false`; фоновой сверки пока нет.

Движок не пишет в `public.agent_runs`. Его SQLite/PostgreSQL остаётся отдельно; если используется та же Supabase PostgreSQL, нужна отдельная схема `ai_engine`, не опубликованная в Data API. Текущие миграции не создают и не изменяют таблицы движка.

## Файлы

Бакет `agent-files` приватный, максимум 10 MiB, разрешены MIME PDF, DOCX, TXT. Формат пути:

```text
<company_id>/<user_id>/<agent_files.id>/<safe_filename>
```

В MVP первые два UUID одинаковы. Фронтенд передаёт файл и `purpose` в `POST /files/upload` Backend 2. Сервер проверяет размер и допустимое расширение, генерирует UUID, сохраняет оригинал в Storage и создаёт `agent_files`. Имя объекта строится сервером как `document.<ext>`, исходное имя сохраняется отдельно. MIME-политика Storage не заменяет проверку содержимого: движок проверяет формат при обработке.

Для исполнения сервер скачивает байты из Storage, загружает их через `POST /files/upload` с соответствующим `purpose`, записывает `engine_file_id` и `engine_synced_at`. В запрос запуска уходят только ID файлов движка. Ссылки Storage движок не принимает. При `404 file_not_found` устаревшее соответствие сбрасывается и файл загружается заново; логика повторного запуска должна учитывать отсутствие идемпотентности.

Клиент может загружать и читать свои объекты. Перезапись, перенос и удаление объектов выполняются через Backend 2: иначе копия в движке и соответствие могут остаться устаревшими. Реализованный поток удаления: пометить `deletion_requested_at`, удалить копию движка (404 считать уже удалённой), удалить объект через Storage API, удалить строку соответствия. При сбое строка сохраняется для повторной очистки. SQL-удаление строк `storage.objects` не заменяет удаление байтов через Storage API.

Две системы не поддерживают общую транзакцию. Синхронизация выполняется перед использованием файла, а очистка — при пользовательском DELETE; фонового сборщика потерянных объектов нет. История запусков и файлов защищена `ON DELETE RESTRICT`: удаление Auth-аккаунта с такими данными требует явного процесса очистки.
