# Исполнение агентов и файлы Backend 2

Платформа опубликована на `https://keme-ai-platform.onrender.com` (локальный вариант — `http://127.0.0.1:8001`) и подключена к отдельному AI Engine на `https://ai-engine-demo.onrender.com`. Альтернативный локальный движок доступен на порту 8002. Текущий стенд использует **mock LLM: демонстрационные ответы, без реальной модели и расходов на провайдера**. Пользовательские запросы принимает Backend 2; engine token выдаётся только сервером.

## Что требуется для запуска

- Зарегистрированный пользователь с ролью `business` и действующей Supabase-сессией.
- Карточка `published`, связанная с `engine_slug`, и одобренная заявка подключения этой компании.
- `SUPABASE_SECRET_KEY=sb_secret_...` в окружении Backend 2 для записи журнала и файлов. Этот ключ не используется фронтендом и не передаётся движку.
- `ENGINE_URL`, отдельный `ENGINE_JWT_SECRET`, одинаковые `aud`/`iss` у двух серверов. Для локального mock-стенда скрипт создаёт игнорируемый Git файл `.run/engine-jwt.key` и оба сервиса используют его при отсутствии переменной.

В проекте Supabase уже есть 12 карточек: три опубликованных демо `marketing`, `support`, `hr` и девять будущих. Регистрация бизнеса и одобрение подключения не выполняются автоматически при наполнении каталога. Роли `developer` и платформенный `admin` не получают исполнительный доступ бизнеса.

## Запуск

`POST /agents/{catalog_slug}/run`, заголовок `Authorization: Bearer <Supabase access token>`:

```json
{
  "message": "Создай контент-план для кофейни",
  "language": "ru",
  "file_ids": [],
  "options": {},
  "history": []
}
```

`message` — 1–8000 символов. Язык `ru`, `kk`, `en`, `auto` (по умолчанию); `kz` не принимается. До десяти UUID файлов **платформы** из `/files/upload`, без повторов. История — до десяти элементов `role=user|assistant`, `content` до 4000 символов. Опции проверяет сам агент по своей JSON Schema. Передать `company_id`, `user_id`, `engine_slug` или свою роль нельзя.

Сервер проверяет сессию, карточку, подключение и владельца каждого файла, синхронизирует нужные файлы, создаёт `agent_runs` со статусом `running` и только затем вызывает движок. Если начальная запись журнала не удалась или серверный ключ не настроен, движок не вызывается. Engine JWT содержит ID пользователя, ID бизнес-профиля и роль `admin` только своей компании; срок по умолчанию 300 секунд.

Ответ HTTP 200:

```json
{
  "platform_run_id": "<platform-run-uuid>",
  "audit_saved": true,
  "execution": {
    "run_id": "<engine-run-uuid>",
    "agent": "marketing",
    "agent_version": "1.0.0",
    "status": "success",
    "response": "Демонстрационный ответ",
    "language": "ru",
    "sources": [],
    "usage": {"input_tokens": 10, "output_tokens": 5, "total_tokens": 15, "estimated_cost": 0, "currency": "USD"},
    "execution_time_ms": 10,
    "mode": "mock",
    "model": "mock",
    "data": {},
    "warnings": []
  }
}
```

`status` также может быть `escalation_required` или `blocked`; это результат выполнения с HTTP 200. `mode=mock` должен быть виден пользователю. Текст ответа может содержать Markdown — фронтенд должен рендерить его с экранированием HTML. `sources.file_id` — ID источника внутри движка; для файловых операций платформы использовать ID из `/files/upload`.

## Журнал и сбои

`GET /runs` и `GET /runs/{platform_run_id}` доступны бизнесу только для своих запусков. Списки используют обычные `limit`, `offset`, `has_more`. Сохраняются только ID и метаданные: статус, язык, провайдер/модель, токены, оценка стоимости, время, машинный код ошибки и счётчики. Запрос, ответ, история, источники и резюме в `agent_runs` не сохраняются.

При ошибке движка сохраняется `error.details.run_id`, если он есть. Сервер отдельно читает `/runs/{engine_run_id}`, чтобы сверить статус/токены/стоимость без повторного исполнения. В ответе ошибки Backend 2 возвращает только безопасные коды и детали `platform_run_id`, `engine_run_id`, `audit_saved`. Текст/произвольные детали ошибки движка не копируются.

**Запуск не повторяется автоматически**, включая 429, 503 и 504. Для нового действия фронтенд соблюдает `Retry-After` и явно сообщает пользователю о повторе. Сетевой таймаут не доказывает, что движок не выполнил задачу. Таймаут движка по умолчанию — 180 секунд, файлового Storage — 60 секунд, Auth — 15 секунд.

Если движок ответил успешно, а финальная запись метаданных не удалась, результат возвращается с `audit_saved=false`; первоначальная строка остаётся `running`. Оператор сверяет её по ID из ответа и журналу движка. При обрыве процесса также может остаться `running`. Фонового согласования таких строк и распределённой гарантии exactly-once в этом этапе нет. Повторный запуск ради исправления журнала недопустим.

## Загрузка и чтение файлов

`POST /files/upload`: multipart `file` и `purpose=brief|knowledge_base|resume|job_description`, с access token бизнеса. Разрешены PDF, DOCX, TXT до **10 MiB**, пустые файлы отклоняются. MIME определяется по допустимому расширению, содержимое дополнительно проверяет движок. Полный multipart ограничен 11 MiB, прочие тела запросов — 512 KiB.

Ответ HTTP 201 — строка `agent_files`: её `id` передавать в `file_ids`. Метаданные содержат исходное имя, назначение, размер и состояние синхронизации. Оригинал хранится в приватном бакете по пути `<company>/<user>/<file UUID>/document.<ext>`; движок получает байты и сохраняет отдельную копию.

`GET /files` и `GET /files/{id}` возвращают только свои метаданные. `GET /files/{id}/download` скачивает оригинал как attachment. Чужой UUID возвращает 404.

Перед запуском cached engine ID проверяется. Если копия движка пропала после его перезапуска, оригинал повторно загружается **до исполнения**. Если движок потерял файл уже между этой проверкой и самим POST run, сервер возвращает ошибку без автоматического повтора. Для Support при восстановлении базы знаний передать UUID нужного KB-файла в `file_ids`; без явных ID движок ищет по уже находящейся у него базе.

Если проверка/обработка файла движком не удалась после сохранения оригинала, ответ ошибки содержит `file_id` и `original_saved=true`: приватный оригинал остаётся для повторной синхронизации или удаления. При сбое записи соответствия сервер пытается удалить новую копию движка. Эти системы не поддерживают общую транзакцию; неудачная компенсация фиксируется кодом в серверном логе без содержимого файла.

## Удаление

`DELETE /files/{id}` помечает `deletion_requested_at`, удаляет копию движка, удаляет объект через Storage API, затем строку метаданных. HTTP 204 означает завершение. Отсутствие копии движка считается успешным удалением. При промежуточном сбое строка остаётся помеченной, повторный DELETE продолжает очистку. Такой файл нельзя использовать в новом запуске. Полностью удалённый/чужой ID возвращает 404.

Пользовательский upload/delete не заменяет хранение жизненного цикла: фоновой уборки незарегистрированных объектов пока нет. Существующий выполняющийся запрос может завершиться после начала удаления файла.

## Состояние и проверка

`GET /engine/health` публично показывает состояние движка, режим и список агентов, без секретов/внутренних настроек. `/health` платформы проверяет сам процесс, а не готовность всех внешних сервисов.

Проходят 99 тестов API и 20 PostgreSQL-сценариев. Отдельные 13 локальных интеграционных проверок используют настоящий engine HTTP/JWT, TXT RAG и PDF/DOCX-парсинг, а Supabase Auth/Storage/журнал заменены изолированным адаптером.

После первоначального локального теста те же 37 проверок пройдены 21 ноября 2026 года с **движком на Render и настоящими Supabase Auth, Storage и PostgreSQL**: вход временного бизнеса, отказ без подключения, заявки, загрузка/скачивание TXT/PDF/DOCX, четыре успешных запуска и одна ошибка HR с журналом, чтение истории, удаление копий и выход. Backend 2 выполнялся через TestClient с настоящими исходящими HTTP-запросами. Подключения одобрялись доверенной тестовой подготовкой данных, а не HTTP-интерфейсом модератора. Пароль оставался в памяти; письма не отправлялись. Тестовый аккаунт/сессии, файлы в обоих сервисах и записи платформы удалены. В движке остаются технические записи пяти запусков и вымышленного tenant: API их удаления нет. Каталог из 12 карточек сохранён; Security Advisor не сообщает замечаний.

Проверка выполнена скриптом `scripts/check_cloud_engine_integration.py` с явным разрешением владельца проекта. Она создаёт и удаляет тестовые данные; не запускать без такого разрешения. Backend 2 с интерфейсом и AI Engine размещены отдельными сервисами Render; 37 проверок повторно пройдены через публичный Backend. реальный LLM-провайдер не подключён. Полный пользовательский signup с подтверждающим письмом, HTTP-сценарий администратора, две компании на общем стенде и восстановление после перезапуска Render остаются отдельными проверками.
