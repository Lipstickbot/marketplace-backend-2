# API каталога и заявок маркетплейса

Локальный адрес — `http://127.0.0.1:8001`, интерактивная спецификация — `/docs`. Здесь описаны каталог и модерация. Запуск и файловый обмен описаны в [ENGINE API](ENGINE_API.md); оплата пока не реализована.

## Каталог

| Метод и путь | Доступ | Действие |
| --- | --- | --- |
| `GET /agents` | Публичный | Опубликованные и будущие карточки |
| `GET /agents/{slug}` | Публичный | Одна карточка |
| `GET /developer/agents` | `developer` | Собственные карточки, включая черновики |
| `GET /admin/agents` | `admin` | Все карточки |
| `POST /admin/agents` | `admin` | Создать карточку |
| `PATCH /admin/agents/{id}` | `admin` | Изменить карточку |

Публичный список поддерживает `category`, `status=published|coming_soon`, `q` (подстрока в имени без учёта регистра), `limit` 1–100 и `offset` 0–10000. Пример: `/agents?category=marketing&status=published&limit=20&offset=0`. Поиск трактует специальные символы буквально. Он не принимает пользовательский SQL или регулярное выражение. Списки упорядочены по `created_at DESC, id DESC`.

Форма каждого списка:

```json
{"items": [], "limit": 20, "offset": 0, "has_more": false}
```

Для следующей страницы увеличить `offset` на `limit`. Сервер читает одну дополнительную запись для `has_more`, не вычисляет общий `COUNT`. При изменении каталога между запросами offset-пагинация не гарантирует неизменный снимок.

Публичные методы всегда работают с анонимными правами, даже при переданном admin token. Черновики и архивные карточки доступны через отдельные защищённые методы. Для скрытой/несуществующей карточки возвращается 404.

Создание карточки, HTTP 201:

```json
{
  "slug": "external-support-assistant",
  "name": "Помощник поддержки",
  "description": "Описание будущего агента",
  "category": "support",
  "status": "coming_soon"
}
```

Редактируются `slug`, `name`, `description`, `category`, `status`, `developer_id`, `engine_slug`, `version`, `supported_languages`, `capabilities`, `accepted_file_purposes`, `input_schema`, `output_schema`. Пустой PATCH и неизвестные поля отклоняются. Явный `null` допускается только для `developer_id`, `engine_slug`, `version`. Если разработчик указан, он должен иметь роль `developer`.

`slug` и `engine_slug` имеют формат `[a-z][a-z0-9-]{0,79}` и уникальны каждый в своей колонке. `published` требует `engine_slug`; если у карточки уже есть история запусков, смена привязки движка запрещена. Указание slug само по себе не проверяет наличие модуля в AI Engine — перед публикацией работающей карточки требуется интеграционная проверка. Внешний код этот API не загружает и не запускает.

## Заявки бизнеса

Для всех запросов нужен Supabase access token и роль `business`:

| Метод и путь | Действие |
| --- | --- |
| `POST /connect-requests` | Заявка к опубликованному агенту |
| `GET /connect-requests` | Свои заявки; фильтр `status` |
| `GET /connect-requests/{id}` | Одна своя заявка |

```json
{"agent_id": "<agent-uuid>", "message": "Хотим подключить агента для нашей компании"}
```

Ответ создания — HTTP 201, строка заявки со статусом `pending`. `company_id` и `requested_by` сервер берёт из проверенного профиля. Клиент не может прислать свои значения владельца, статуса и модератора. К `coming_soon`, черновикам и архивным карточкам подключиться нельзя. Для чужой заявки возвращается 404. На пару компания/агент допускается одна заявка; повторная подача возвращает 409, включая ранее отклонённую заявку. Повторное открытие и отзыв подключения пока не реализованы.

Одобрение заявки даёт запись разрешения для будущего запуска. Оно не включает оплату и само не вызывает движок. Перед будущим запуском сервер также обязан заново проверить, что карточка опубликована.

## Заявки разработчика

Нужен access token и роль `developer`:

| Метод и путь | Действие |
| --- | --- |
| `POST /agent-submissions` | Создать заявку |
| `GET /agent-submissions` | Свои заявки; фильтр `status` |
| `GET /agent-submissions/{id}` | Одна своя заявка |

```json
{
  "name": "Помощник продаж",
  "description": "Какие задачи решает агент и как его подключить",
  "category": "sales",
  "repository_url": "https://github.com/example/sales-agent"
}
```

`repository_url` необязателен, допускается HTTPS без встроенного логина/пароля. Содержимое репозитория сервер не загружает. `developer_id` выставляется из сессии. Новая заявка имеет статус `pending`; клиент не может одобрить себя, назначить готовую карточку или подменить автора. Изменение уже поданной заявки в этой версии не реализовано.

## Модерация

Нужен access token пользователя с ролью `admin` в `profiles`:

| Метод и путь | Действие |
| --- | --- |
| `GET /admin/connect-requests` | Все заявки бизнеса |
| `POST /admin/connect-requests/{id}/review` | Рассмотреть подключение |
| `GET /admin/agent-submissions` | Все заявки разработчиков |
| `POST /admin/agent-submissions/{id}/review` | Рассмотреть публикацию |

У административных списков есть пагинация и фильтр `status=pending|approved|rejected`.

Подключение или отклонение заявки:

```json
{"decision": "approved", "review_note": "Подключение разрешено"}
```

Одобрение заявки разработчика дополнительно требует slug будущей карточки:

```json
{"decision": "approved", "publication_slug": "sales-assistant", "review_note": "Принято в каталог"}
```

Для отклонения передать `decision: "rejected"` без `publication_slug`. Комментарий необязателен, максимум 4000 символов. `reviewed_by` и `reviewed_at` база заполняет сама.

Рассмотреть можно только `pending`. Строка блокируется до конца транзакции: повторный/конкурентный запрос после первого решения получает 409 `already_reviewed`. Одобрение публикации создаёт **одну карточку `coming_soon` без `engine_slug`** из проверенной заявки и сохраняет `published_agent_id`. При занятом slug вся транзакция откатывается, заявка остаётся `pending`.

FastAPI проверяет роль; закрытая функция PostgreSQL дополнительно проверяет роль из БД и наличие сессии. Публичные RPC работают как `SECURITY INVOKER`. Сервисный ключ и прямые UPDATE-права клиенту не выдаются. Обход FastAPI прямым вызовом RPC не обходит эти проверки.

Роль `admin` назначает доверенный оператор конкретному уже зарегистрированному профилю. API регистрации эту роль не выдаёт; автоматическое назначение реальному пользователю не выполнялось.

## Ошибки и проверки

Формат ошибки такой же, как у Auth API: `{"error":{"code","message","request_id"}}`. Для защищённых запросов нужен `Authorization: Bearer <access_token>`. Ответы имеют `Cache-Control: no-store`.

| HTTP | Код | Причина |
| --- | --- | --- |
| 401 | `auth_required`, `invalid_session`, `session_revoked` | Нет действующей сессии |
| 403 | `role_forbidden` | Неверная роль |
| 404 | `not_found` | Запись не существует или недоступна |
| 409 | `duplicate_record` | Занят slug или повторная заявка подключения |
| 409 | `already_reviewed` | Решение по заявке уже принято |
| 422 | `validation_error`, `invalid_data`, `invalid_reference` | Некорректные поля или нарушение правил модели |
| 502/503 | `supabase_contract_error`, `supabase_unavailable`, `schema_not_ready` | Сбой сервиса/несовпадение схемы |

Всего пройдены 97 тестов API и 20 проверок PostgreSQL. `supabase/checks/marketplace_smoke.sql` выполняет проверки модерации на реальной Supabase PostgreSQL и откатывает все синтетические строки. Полный HTTP-сценарий администратора на реальном пользовательском аккаунте требует отдельно назначенного администратора; сейчас API проверен через mock HTTP, а транзакции — непосредственно в облачной БД.
