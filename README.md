# Backend 2 для B2B маркетплейса ИИ агентов

Платформенная часть маркетплейса: бизнес выбирает и подключает агента, разработчик подаёт заявку на публикацию, администратор модерирует каталог. Исполнение Marketing, Support и HR остаётся в отдельном AI Engine друга.

## Первый этап

Применены три SQL-миграции: пять таблиц из задания (`profiles`, `agents`, `connect_requests`, `agent_submissions`, `agent_runs`), дополнительная таблица `agent_files` для связи Storage с движком, приватный бакет `agent-files` и оптимизация политик каталога. Созданы индексы, ограничения, RLS и триггер профиля при регистрации.

Схема развёрнута в [проекте Supabase](https://supabase.com/dashboard/project/qxzhrkchmzmfxvkpnbfr) 21 ноября 2026 года. API URL: `https://qxzhrkchmzmfxvkpnbfr.supabase.co`. Все шесть таблиц защищены RLS; бакет приватный, лимит 10 MiB. В проверке безопасности Supabase замечаний нет.

Миграции проходят 20 сценариев в PostgreSQL через PGlite. Дополнительно на облачной базе выполнены `supabase/checks/smoke.sql` и `supabase/checks/marketplace_smoke.sql`: проверены регистрационный триггер, защита ролей, изоляция пользователей, права на файлы, создание карточек и транзакции модерации. Все синтетические строки откатились, включая тестовых Auth-пользователей и сессии.

Готовы API авторизации, каталога, заявок и интеграция AI Engine. В Supabase добавлены 12 публичных карточек: три демо и девять `coming_soon`. Backend 2 и интерфейс опубликованы на **https://keme-ai-platform.onrender.com** и подключены к AI Engine друга на `https://ai-engine-demo.onrender.com`. Полная связка с настоящими Supabase Auth/Storage/PostgreSQL и движком на Render прошла 37 проверок 21 ноября 2026 года. LLM работает в mock-режиме. Интерфейс Keme AI подключён локально: каталог, вход, кабинет бизнеса, заявки разработчика и модерация. Оплата пока не реализована.

## Запустить проверки

Нужны Node.js 22+ и pnpm для тестов SQL, Python 3.13 для FastAPI. Node используется только для проверки базы.

```powershell
pnpm install --frozen-lockfile
pnpm test
```

20 тестов SQL применяют миграции целиком в PostgreSQL и выполняют запросы от ролей `anon`, `authenticated`, `service_role`. Системные таблицы Auth/Storage заданы тестовой фикстурой. Доставка подтверждающего письма и файловый обмен с настоящим Supabase Storage требуют отдельной проверки на стенде.

## Второй этап и запуск API

FastAPI предоставляет регистрацию, вход по почте/паролю, обновление токенов, выход из текущей сессии, чтение и изменение своего профиля. Для определения роли сервер читает `profiles`, для проверки токена обращается к Supabase Auth, затем проверяет наличие сессии. Сервисный/секретный ключ для этих операций не используется: доступ к профилю идёт с пользовательским токеном и RLS.

В локальном `.env` уже записаны URL и publishable key текущего проекта; файл исключён из Git. Для новой установки скопировать `.env.example` в `.env` и заполнить publishable key. Для Auth/каталога секрет движка не нужен; исполнение и файлы настраиваются ниже.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest backend/tests -q
.\scripts\start-backend.ps1
```

Из любой ОС при установленных зависимостях запуск из корня репозитория:

```text
python -m uvicorn backend.app.main:create_app --factory --host 127.0.0.1 --port 8001
```

Проверка сервера: [health](http://127.0.0.1:8001/health), интерактивная документация [Swagger](http://127.0.0.1:8001/docs). Backend 2 использует порт 8001; публичный общий сайт — https://keme-ai-platform.onrender.com. Текущий движок работает на Render. Альтернативный локальный AI Engine использует порт 8002.

| Метод и путь | Действие |
| --- | --- |
| `POST /auth/signup` | Регистрация `business` или `developer`; `admin` запрещён |
| `POST /auth/login` | Вход по email/password и получение токенов/профиля |
| `POST /auth/refresh` | Обновление по refresh token |
| `POST /auth/logout` | Выход из текущей сессии |
| `GET /auth/me` | Свой профиль и роль |
| `PATCH /auth/me` | Только `display_name`, `company_name` |

Всего проходят 99 тестов API (из них 29 — авторизация) и 20 проверок PostgreSQL. На реальном Supabase выполнены 13 проверок входа, профиля, обновления и отзыва сессии с разрешённым временным аккаунтом. Аккаунт, его профиль, identity и сессии удалены; временный файл с паролем также удалён. Тестовая учётная запись была предварительно подтверждена для проверки без отправки почты; доставка письма и полный пользовательский signup пока не проверялись. В Security Advisor после миграций замечаний нет.

Подробные JSON-примеры и правила работы фронтенда — в [контракте Auth API](docs/AUTH_API.md).

## Третий этап и API маркетплейса

Реализованы публичный каталог и карточка, поиск по имени, фильтры категории/статуса, пагинация, заявки бизнеса на подключение, заявки разработчика на публикацию и административная модерация. Владельцы определяются сервером из сессии. Публичный каталог возвращает только `published` и `coming_soon`, даже если запрос содержит токен администратора.

Администратор создаёт и редактирует карточки, рассматривает заявки. Проверка его роли выполняется дважды: в FastAPI и внутри транзакции PostgreSQL с проверкой живой сессии. Привилегированные функции находятся в закрытой схеме `private`; публичные RPC-обёртки работают без повышения привилегий. Сервисный ключ для модерации не нужен.

Одобрение заявки разработчика атомарно создаёт карточку `coming_soon` и сохраняет связь в заявке. Внешним агентам пока не назначается исполнитель AI Engine. Повторное рассмотрение возвращает 409; конфликт slug откатывает всю публикацию, сохраняя `pending`. Изменить привязку движка у карточки с историей запусков нельзя.

В облачной базе пройдена транзакционная проверка создания карточек, ролей, заявок, одобрения и отката публикации; все тестовые записи откатились. Полный HTTP-сценарий модератора с отдельным постоянным аккаунтом пока не выполнялся. Администратор должен быть назначен оператором существующему профилю; регистрация роль `admin` не выдаёт.

Все endpoints видны в [Swagger](http://127.0.0.1:8001/docs). Методы, JSON-примеры и ограничения описаны в [контракте API маркетплейса](docs/MARKETPLACE_API.md).

## Четвёртый этап и AI Engine

Реализованы запуск агента после проверки опубликованной карточки и одобренной заявки, короткоживущий engine JWT, история запусков без текстов, загрузка PDF/DOCX/TXT в приватный Storage, синхронизация с движком и удаление обеих копий. Браузер передаёт UUID файлов платформы; сервер сам заменяет их ID движка. Автоматического повтора исполнения нет.

В каталоге три карточки `marketing`, `support`, `hr` со статусом `published` и девять `coming_soon` без исполнителя. Метаданные и JSON Schema трёх демо взяты из реального локального движка. Демо и ответы явно помечены как mock; реальная модель не подключена, внешних LLM-вызовов нет.

Для записи `agent_runs`, метаданных файлов и работы с Storage нужен серверный `SUPABASE_SECRET_KEY=sb_secret_...` в локальном `.env`. На текущем стенде ключ настроен, доступ проверен, API перезапущен. В чат и Git ключ не копировать. Без него API возвращает `503 runtime_storage_not_configured` **до запуска агента**. Auth, каталог и модерация работают с publishable key и пользовательскими JWT. После изменения `.env` сервер нужно перезапустить.

Настройка отдельного окружения движка и запуск в другом терминале:

```powershell
.\scripts\setup-engine.ps1
.\scripts\start-engine.ps1
```

Скрипт использует неизменённый репозиторий друга на проверенном коммите и закреплённые зависимости из `runtime/engine-requirements.lock.txt`. Локальный ключ подписи создаётся в `.run/engine-jwt.key`, исключённом из Git; оба локальных сервиса читают его, если `ENGINE_JWT_SECRET` не задан. SQLite и файлы локального движка также находятся в `.run`. Для Render задать `ENGINE_URL=https://ai-engine-demo.onrender.com` и отдельный `ENGINE_JWT_SECRET` у Backend 2; у движка тот же секрет называется `JWT_SECRET`. Настройки движка: `JWT_ALGORITHM=HS256`, `JWT_AUDIENCE=ai-engine`, `JWT_ISSUER=marketplace-backend`. Новые переменные Render применяются через **Save and deploy** или новый деплой; **Restart service** использует прежние значения переменных.

Локальная проверка с настоящим движком, но изолированными тестовыми Auth/Storage/журналом Supabase:

```powershell
.\.engine-venv\Scripts\python.exe scripts/create_engine_fixtures.py
.\.venv\Scripts\python.exe scripts/check_local_engine_integration.py
```

Пройдены 13 изолированных проверок с настоящим движком: Marketing, Support с RAG по TXT, HR с DOCX, Marketing с PDF, ошибка HR без резюме, история и удаление копий.

После первоначальной проверки с локальным движком те же **37 проверок** через `scripts/check_cloud_engine_integration.py` успешно выполнены с AI Engine на Render: настоящий Supabase Auth, создание бизнес-заявок, загрузка/скачивание TXT/PDF/DOCX в приватном Storage, четыре успешных запуска и одна корректная ошибка с записью в `agent_runs`, история, выход и очистка. HTTP-код Backend 2 выполнялся через TestClient с настоящими исходящими HTTP-запросами. Подключения одобрялись доверенной тестовой подготовкой данных; HTTP-сценарий модератора этим не проверяется. LLM оставался mock, письма не отправлялись. Временный аккаунт, его сессии, три файла в обоих сервисах и созданные заявки/запуски Supabase удалены. В движке остаются технические метаданные пяти запусков и вымышленного tenant: API их удаления нет. Все 12 карточек каталога сохранены; Security Advisor без замечаний.

Повторный облачный тест создаёт и удаляет данные, поэтому запускается только с разрешением владельца проекта. Для обычного пользовательского запуска нужны собственная регистрация бизнеса и одобренные подключения.

Контракт и поведение при сбоях — в [ENGINE API](docs/ENGINE_API.md).

## Подключение и повторное развёртывание Supabase

Текущий проект уже настроен: повторно выполнять миграции в SQL Editor не нужно. Следующие шаги предназначены для нового пустого проекта или настройки будущего бэкенда.

1. Открыть [Supabase Dashboard](https://supabase.com/dashboard), создать организацию при необходимости и новый проект. Выбрать доступный регион ближе к пользователям, задать уникальный пароль базы и сохранить его в менеджере паролей.
2. Дождаться готовности базы. Для нового пустого проекта можно открыть SQL Editor и выполнить все файлы `supabase/migrations/*.sql` по порядку версии. Не запускать повторно: это версионированные миграции, а не скрипт пересоздания таблиц. Предпочтительный способ с историей миграций — CLI или Supabase MCP `apply_migration`.
3. Выполнить `supabase/checks/verify.sql`. Ожидаются шесть таблиц с `rls_enabled = true`, приватный бакет с лимитом `10485760`, один триггер `on_auth_user_created` и отсутствие опасных прав записи у `anon`/`authenticated` в последнем результате.
4. В Table Editor проверить таблицы, в Storage — приватный `agent-files`. В Auth включить Email/Password и подтверждение почты; задать Site URL и разрешённые Redirect URLs для реального фронтенда. Локальный `config.toml` не меняет настройки облачного проекта.
5. Скопировать `.env.example` в `.env` и заполнить значения локально. URL текущего проекта уже указан; publishable key можно получить в настройках подключения/API проекта. Секретный серверный ключ хранится только на сервере, для новых интеграций предпочтителен `sb_secret_...`. `ENGINE_JWT_SECRET` потребуется на этапе вызова движка и должен совпасть с `JWT_SECRET` движка.

Альтернатива SQL Editor — [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started). Команды ниже проверены по `--help` версии **3.2.0**. В CLI 3 удалённое назначение задаётся явно:

```powershell
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase migration list --remote
supabase db push --remote --dry-run
supabase db push --remote
```

Выбрать один способ применения. Для существующей базы сначала нужен анализ схемы: миграции создают новые таблицы, а не преобразуют произвольную старую структуру. Если миграции уже выполнялись через SQL Editor, перед переходом на CLI нужно согласовать историю миграций; повторный `db push` на такую базу запускать нельзя.

Полный локальный стенд с установленным CLI и контейнерной средой:

```powershell
supabase start
supabase db push
```

## Архитектура интеграции

```text
Фронтенд → Supabase Auth → Backend 2 → AI Engine
                             │
                             └→ Supabase PostgreSQL и Storage
```

Backend 2 проверяет сессию и доступ бизнеса, выпускает короткий engine token и передаёт его движку. Сырой Supabase access token движок не принимает. Решения по полям, ролям и файлам описаны в [контракте Backend 2](docs/INTEGRATION_DECISIONS.md).
